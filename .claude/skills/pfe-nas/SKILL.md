**Working ASP runtime env on pfe (the dev BinaryBuilder build).** A bare `export PATH=.../StereoPipeline/bin` is NOT enough - the binaries link ISIS/CSM and die with `libusgscsm.so.1: cannot open shared object` then `IsisPreferences not found`. There is **no `asp_deps` env on pfe anymore** (only `asp_deps_stale_nfs`); the live ISIS env is **`isis10asp`**. The env that works (source a file like `asp_env.sh`):
```
SP=$HOME/projects/BinaryBuilder/StereoPipeline
export ISISROOT=/swbuild/oalexan1/miniconda3/envs/isis10asp
export PATH=$SP/bin:$SP/libexec:$PATH
export LD_LIBRARY_PATH=$ISISROOT/lib:$SP/lib:$SP/lib/csmplugins:$LD_LIBRARY_PATH
export GDAL_DATA=$SP/share/gdal PROJ_DATA=$SP/share/proj PROJ_LIB=$SP/share/proj
```
The **key** missing piece is `$ISISROOT/lib` on `LD_LIBRARY_PATH`. (`cam_gen` and other non-ISIS tools run without it; `mapproject`/`stereo`/`point2dem` need it.)

**You may build your own conda envs on pfe.** `$HOME/miniconda3` is a symlink to `/swbuild/oalexan1/miniconda3`, so a plain `conda create -n <name> ...` lands on swbuild automatically (matches the existing env layout - that is the intended pattern). Do this when the ASP-bundled python lacks what an analysis script needs. Made 2026-08-26: env **`geo`** = `gdal numpy scipy matplotlib pyproj` (the ASP python has no matplotlib/scipy; conda base has no osgeo). `conda activate geo` to run analysis `.py` natively on pfe instead of pulling data to the Mac.

Bare minimum to remember without reading:
- **DRY-TEST EVERY qsub SCRIPT ON THE HEAD NODE BEFORE SUBMITTING - NO EXCEPTIONS.**
  Never burn a queue+run to find a trivial bug (a `cd` that breaks relative paths, a
  missing input, a bad `-t` session, an arg typo); these die in the first SECONDS.
  Run the REAL script briefly on the head node, WATCH ram/cpu, KILL within ~30s (or
  the instant memory/cpu spikes - the head node OOMs and the gate reaps you), INSPECT
  the log/products, then WIPE every produced file individually. Only submit the real
  qsub after a clean dry test. Recipe: `setsid bash script.sh <args> >/dev/null 2>&1 &`
  then `ps -o pid,rss,pcpu,comm -u $USER --sort=-rss` a couple times, then
  `pkill -KILL -u $USER -f '<toolnames incl bundle_adjust|parallel_stereo|stereo_|mapproject|point2dem|wv_correct|gdal_translate>'`;
  read the script's `exec>` log (it says what it wrote) and `ls` the run dir; then
  `rm -rf <literal absolute path to the run subdir>`. This keeps recurring (burned
  again 2026-08-28: a `cd v5` broke `data/...` paths, bundle_adjust exit 1, whole
  job dead - a 30s dry test would have caught it). The old "4-sec dry-run" note below
  means exactly this. Same for CLAUDE.md.
- **No heavy/parallel compute on the pfe head node** - `parallel_stereo`, anything multi-process/multi-thread or big-RAM goes to qsub (small/fast -> `devel`). Light single-thread `gdalinfo`/`gdal_translate`/`gdalwarp`/`ls`/`qstat` on the head node is fine (don't qsub a one-off gdalinfo - use common sense). **HEAD-NODE RULE (pfe AND Athena front end), confirmed by a policy-violation warning 2026-08-07: the trigger is >1 process/thread, NOT file size. On any head node use ONLY 1 PROCESS and 1 THREAD. Big single-threaded `gdal_translate`/`gdalwarp`/`geodiff`/`dem_mosaic --threads 1` on multi-GB rasters are all FINE. `dem_mosaic --threads 6` (or any multi-thread/multi-process) is the violation. So when downsampling/differencing/mosaicking for figures on a head node, force `--threads 1`; anything heavier goes to a qsub compute node (or do it locally on the Mac).** **IF THE HEAD NODE KILLS a command (policy enforcement / OOM), DO NOT retry it on the head node - that just re-trips the gate. Move that work to a qsub compute node (or shrink it to 1 proc / 1 thread / low mem). Retrying a killed head-node command is never the fix.** **To run any gdal/ASP tool on pfe FIRST set the env** (non-interactive ssh has nothing on PATH, PROJ unset): `conda activate asp_deps` (PROJ data, so `-t_srs` works) + `export PATH=$HOME/projects/BinaryBuilder/StereoPipeline/bin:$PATH` (the packaged build has ALL tools); detail in `~/projects/pleiades_notes.sh`. **NEVER run heavy compute - `stereo_corr`/`parallel_stereo`/correlation (the eval dd) - on the Mac OR the pfe head node; it goes to a qsub compute node.** The eval (`cassis_eval_stage.sh`) is the last step inside each stage's qsub job, so its dd runs on the compute node - do not run it by hand on the Mac. 4-sec dry-run before qsub. budget `e2305`. **Models & node choice:** `cas_ait` (40c, Aitken), `rom_ait`/`mil_ait` (128c, Aitken), `bro_ele` (28c, Electra), `sky_ele` (40c, Electra). Broadwell is decommissioned ONLY on Pleiades - `bro_ele` (Electra) and `sky_ele` are FINE to use. **Our code is model-agnostic - it must run on ANY of them** (match `ncpus` to that model's cores). **Before launching, study load on ALL systems** (`/u/scicon/tools/bin/node_stats.sh` -> Free vs "Queued jobs want N nodes" per model) and pick the LEAST-CONTENDED (e.g. bro_ele was Free 292 / 12 queued while cas_ait was 379 queued). **For small single-node jobs Athena (Turin) nodes are also fine - but Athena Turin is only visible/submittable from the ATHENA front-end** (ssh to athena), NOT from pfe. **If a job sits queued too long, qdel it and resubmit on a less-contended system.** In a non-interactive ssh, qsub is not on PATH - use `/PBS/bin/qsub`. `devel` allows only 1 job/user (pack multiple sites into ONE serial job). POLICY: NO separate PBS launcher script (cannot afford one per stage). The PLAN/NOTES file holds the COMPLETE, LITERAL, copy-pasteable qsub command line (the full `qsub <all pbs args> -- $dir/script.sh <all script args, workDir LAST>` as ONE reproducible string - NOT just the args/params/job-id logged piecemeal), WITH its rationale + named params, logged BEFORE the launch. Then launch the worker DIRECTLY via that qsub `--` form. The worker self-handles umask/cd/tailable-log and cds into the passed workDir; it holds only tool commands, never qsub args. This is GENERAL, INDEPENDENT of allocation (e2305/s3319/any) - it is about code structure. Only a LARGE fan-out (hundreds of jobs, rare) justifies a generic launcher; most work needs one qsub or a handful, so inline-in-notes is the default. Detail: `~/projects/qsub_rules.sh`, `qsub_convention.sh`.
- **ASP tools DEFAULT TO MULTI-THREAD, so as a RULE they trip the head-node >1-thread gate and get KILLED - and each kill fires an unhappy NAS policy-violation email (a real cost, avoid it).** So send ASP tools (`bathy_plane_calc`, `bundle_adjust`, `point2dem`, `dem_mosaic`, `parallel_stereo`/`stereo_*`, etc.) to qsub (`devel` for short/iterative - fast turnaround, 1 job/user), NOT the head node - even a "quick" one, because it spins up ~8 threads by default and reads big rasters. Reserve the head node for genuinely light SINGLE-THREAD gdal streaming only (`gdalinfo`, `gdal_translate`/`gdalwarp`/`geodiff` with `--threads 1`, `ls`, `qstat`). Burned 2026-08-25: `bathy_plane_calc` on a 1.5 Gpx PAN mask defaulted to 8 threads and was reaped at 31% (and NAS emailed about it). Do NOT retry on the head node (re-trips the gate + another email) - qsub it.
- **Head/front-end nodes HAVE outbound internet - that is a MAIN PURPOSE of them (downloads, transfers, git, rclone/gdown/curl/wget, pip/conda installs). COMPUTE nodes do NOT have internet.** So run any data download or transfer (Google Drive via rclone, `git clone`/`pull`, `curl`) ON the head/front-end node - NEVER inside a qsub compute job (no network there). This is the flip side of the no-compute rule: head node = network + light single-thread I/O; compute node = CPU/RAM, no network. A download is network-bound, not compute, so it does NOT trip the >1-thread gate. (Confirmed 2026-08-26: a 4.9 GB rclone pull from Google Drive ran at ~294 MiB/s on the pfe head node.) For Google Drive specifically see the `google-drive` skill (rclone headless-auth recipe).
- **Finding GDAL / `gdalinfo` on pfe (default non-interactive login PATH has NONE).** Two reliable, self-contained sources, call by ABSOLUTE path: (1) the ISIS conda envs `/vast_swbuild/swbuild/oalexan1/miniconda3/envs/isis10asp/bin/gdalinfo` (also `isis10`, `usgscsm_cassis`) - GDAL_DATA/PROJ are wired inside the env, so projection reads and `-t_srs` work without activating; (2) **ASP's own packaged bundle** `/vast_swbuild/swbuild/oalexan1/projects/BinaryBuilder/StereoPipeline/bin/` (and `libexec/`) ships `gdalinfo`/`gdal_translate`/`gdalwarp`/etc. - **ASP includes GDAL**; call it directly for plain info, and for projection/`-t_srs` set `GDAL_DATA`/`PROJ_LIB`/`PROJ_DATA` to the bundle's `share/` (or `conda activate asp_deps`). To DIG when unsure of the path: `find /vast_swbuild/swbuild/oalexan1 /nobackupnfs1/oalexan1 -maxdepth 6 -name gdalinfo -type f`. Plain `which gdalinfo` / `conda env list` return nothing in a non-interactive `bash -lc` shell - don't conclude GDAL is absent.
- **Keep ssh command bodies DUMB - no funny shell metacharacters passed over ssh.** A single-hop `ssh pfe 'bash -lc "echo === foo (bar) ==="'` dies with `syntax error near unexpected token '('` - parens, backticks, `$(...)`, and `{...}` inside `echo`/marker strings trip the local or remote shell. Use simple `===tag===` markers (no spaces, no parens), avoid `$`/backticks/globs inline, and put anything with quotes, vars, or multiple statements in a small script run by ABSOLUTE path. (Same spirit as the double-hop rule below, but it bites on single hops too.)
- **On pfe, NEVER rely on the default `ssh`/`scp` landing dir - it is the HOME dir
  (`/home6/oalexan1`), so scratch dropped there litters the home (which has even been a
  stray olegmisc checkout at times).** This is the mechanism behind the recurring pile-up of
  `inspect_*.sh` / `*.py` / `print.prt` in `~`: `ssh pfx 'python foo.py'` runs with CWD=`~`,
  `scp file pfx:` lands in `~`, and ISIS/gdal tools dump `print.prt`/`.aux.xml` into CWD. FIX
  (do it at the moment of writing, every time): every remote script goes to `pfx:/tmp/...`
  explicitly (`scp file pfx:/tmp/`, run `ssh pfx bash /tmp/file.sh`); `cd` into a work dir
  before running any tool so its side-outputs land there, not in `~`; anything worth keeping
  goes in a project subdir. Never the bare default.
- **NEVER wipe anything on lfe.** lfe access from l1: `ssh pfx` then `ssh lfe`.
- **Staging a file off tape (`dmget`): launch it DETACHED, decoupled from the poll - burned TWICE (2026-08-20).** A large file (tens of GB) can take many minutes to stage. If `dmget` runs foreground inside a backgrounded Bash task or a poll/Monitor loop, and that task is later killed (session lifecycle, TaskStop, context compaction, a killed monitor), the `dmget` process dies with it and the file stalls half-staged at `(UNM)` - you then have to re-issue and wait all over again from scratch. RULE: on lfe, FIRST launch `dmget` as a detached `nohup ... &` writing to a log (so it survives everything), THEN poll `dmls -l` for `(DUL)`/`(REG)` in a SEPARATE task; killing the poller never touches the stage. E.g. `ssh pfx "ssh lfe 'cd /u/oalexan1 && nohup dmget projects/foo.tgz > dmget_foo.log 2>&1 & echo pid \$!'"`, then in its own loop poll `dmls -l projects/foo.tgz` until it shows `(DUL)`/`(REG)`. If a poll finds it still `(UNM)` with no `dmget` running (`ps -u oalexan1 | grep -c dmget` == 0), the stage was orphaned - relaunch the detached `dmget`. (States: `OFL`/`DUL` = on tape, `UNM` = unmigrating/mid-stage, `REG`/`MIG` = on lfe disk / migrating.) READ-TRIGGERS-STAGE shortcut (often simplest): any READ of an `(OFL)` file auto-triggers DMF staging - so `scp lfe:/u/.../file.zip .` (pfx pulling to /nobackup) or starting the `unzip`/`tar xf` of the archive will itself block-then-stage, no explicit `dmget` needed. Do that pull/untar INSIDE a backgrounded Bash task (or nohup on lfe); if it dies mid-stage nothing is orphaned - just re-run the read and DMF resumes. For MANY/large files still prefer the explicit detached `dmget` above so the stage survives independently of the copy. Do NOT unzip in place on lfe (writes to tape space) - `scp` the archive to `/nobackupp19` first, then unzip there. Burned before by running `dmget` foreground in a killable task (2026-08-22): background it.
- **Double-hop ssh quoting (Mac -> pfx -> lfe/athfe01): use OUTER double quotes, INNER single quotes, and ONE trivial pipeline** - `ssh pfx "ssh lfe 'tar tzf f | head'"`. This keeps recurring: `ssh pfx 'ssh lfe "..."'` with `===` markers, `$VAR`, `awk` using `$N`, or multiple `;`-separated echoes INSIDE gets eaten by the outer Mac shell and the command breaks ("=== not found"). So on a double hop: no `===`, no `$`, no `awk $N`, no `;`-chains inside; just a single simple command. For anything with quotes/vars/multiple statements, write a small script and run it by ABSOLUTE path (`/home6` is shared across pfe + Athena, so a script there runs on athfe01 too; for lfe, `scp` the script to lfe first). Keep the inner command dumb. (Fixed 2026-08-20 after breaking it twice in one session.)
- `/home6` data MUST symlink to `/nobackup*`. Symlink-wipe procedure in `pleiades_notes.sh`.
- **Every qsub script: `exec >` redirect to a work-dir log (never PBS `-o`) AND `umask 022` (readable outputs). Details: `qsub_convention.sh` / `qsub_rules.sh`.**
- **CHECK JOB EFFECTIVENESS on any long/multi-node pfe job - do not assume it parallelizes.** Effectiveness (efficiency) = CPU-time-used / (cores-allocated x walltime); 1.0 = every allocated core busy every second, low = idle cores wasting the allocation. THE overall number is `qstat`'s `Eff` column, equivalently from `qstat -f <jobid>`: `resources_used.cput / (resources_used.ncpus x resources_used.walltime)`. This is already JOB-WIDE - `cput` sums CPU-time over ALL nodes/chunks and `ncpus` is the TOTAL cores - so for a MULTI-NODE run it covers every node at once; you do NOT poll each node to get the overall figure (that answers "is the whole job effective"). Instantaneous aggregate = `resources_used.cpupercent` (divide by 100 = cores busy right now, summed across all nodes; e.g. 529 = 5.3 of 28). Any LOW value SUSTAINED over time (e.g. 7% on 28 cores = ~2 cores busy) is SUSPECT - investigate, do not ignore. To then LOCALIZE which node/rank is the laggard in a multi-node job: `exec_host`/`exec_vnode` in `qstat -f` lists every node; ssh each and compare `uptime` load avg vs its core count (pdsh/clush across all at once if available). Common cause: a serial per-item loop starving the node -> fix is batching/concurrency across items, not bigger per-item threads. Caveat: cput-efficiency can look low for legitimately I/O-bound or sync-heavy phases - judge over time, not one instant. (Caught the un-batched Jezero stereo_transverse.sh this way, 2026-06-26: Eff 7%, cpupercent 529.)
